4. PHASE 2 — SÉCURITÉ ET AUTORISATIONS
================================================================================

4.1 Défense en profondeur

Pour chaque module Commercial, vérifier quatre niveaux :

A. Navigation
- lien visible uniquement si l’utilisateur peut réellement accéder au module ;
- absence de lien ne constitue jamais l’unique protection.

B. Page
- chargement interdit ou redirection sûre sans permission ;
- pas de flash de contenu sensible avant contrôle ;
- états 401 et 403 distincts si la convention du projet le permet.

C. API
- chaque GET exige la permission read/use correcte ;
- chaque POST/PATCH/PUT/DELETE exige write/accept appropriée ;
- ne jamais faire confiance au rôle ou au prix envoyé par le client.

D. Payload
- sérialisation minimale selon permission ;
- suppression côté serveur des champs sensibles ;
- aucun calcul dérivé exposé permettant de retrouver la marge.

4.2 Matrice cible minimale

Confirmer dans le registre réel, puis aligner :
- clients* : clients:read / clients:write ;
- pos*, pricing simulate, cart* : pos:use ;
- marge POS : pos:view_margin ;
- devis* : devis:read / devis:write / devis:accept selon action ;
- commandes* : commandes:read / commandes:write ;
- réclamations* : permissions actuelles clients:read / clients:write.

Ne pas introduire immédiatement reclamations:* si cela casse les rôles existants.
Si la séparation est pertinente :
- ajouter les nouvelles permissions de façon additive ;
- prévoir une compatibilité temporaire avec clients:* ;
- documenter le plan de migration ;
- tester tous les rôles ;
- aucune perte d’accès légitime.

4.3 POS-03 — assainissement de /api/pos/price-preview

Corriger l’endpoint réel :
- réutiliser le même mécanisme que /api/pricing/simulate ;
- appliquer sanitizePricingPayloadForRole ou l’abstraction canonique équivalente ;
- assainir objets imbriqués, tableaux, totaux et métadonnées ;
- ne pas seulement masquer la colonne dans l’interface ;
- vérifier les logs, exports, erreurs et réponses JSON.

Tests obligatoires :
- pos:view_margin reçoit uniquement les champs prévus ;
- pos:use sans pos:view_margin ne reçoit aucune marge/coût ;
- utilisateur sans pos:use reçoit 403 ;
- utilisateur non authentifié reçoit 401 ;
- snapshots ou assertions profondes empêchent la réapparition des champs.

4.4 CRM-04 — données financières client

Inventorier solde, CA, encours, plafond, marge et historique financier.
Décider selon les permissions existantes, sans inventer une convention :
- gate finance déjà existant, ou ;
- permission dédiée additive.

Appliquer le filtrage côté API et côté UI.
Un utilisateur clients:read ne doit pas obtenir automatiquement des données
financières sensibles si son rôle métier ne les nécessite pas.

5. PHASE 3 — SAV, RÉCLAMATIONS ET DEEP-LINKS
================================================================================

5.1 REC-01 — afficher et lier la commande

Dans la liste des réclamations :
- charger la relation commande de manière contrôlée ;
- afficher commande.numero ou identifiant métier canonique ;
- ajouter un lien vers /commandes/[id] ;
- gérer une réclamation legacy sans commande sans crash ;
- éviter N+1 ;
- conserver filtres et pagination.

5.2 REC-02 et CRM-03 — création de réclamation

Ajouter un formulaire cohérent sur /reclamations et depuis la fiche client :
- commandeId optionnel si le modèle le permet réellement ;
- sélecteur limité aux commandes du client sélectionné ;
- si commande choisie, déduire/valider le client côté serveur ;
- empêcher l’association commande/client incohérente ;
- afficher numéro, date, statut et montant utile dans les choix ;
- recherche ou pagination si nombreuses commandes ;
- validation partagée client/serveur ;
- messages d’erreur explicites ;
- protection contre doubles soumissions.

Ne jamais accepter aveuglément clientId + commandeId du navigateur.
L’API doit vérifier que la commande existe, est accessible et appartient au client.

5.3 REC-03 — erreurs réseau

Remplacer tout « catch → [] » ou faux état vide par :
- état de chargement ;
- état vide uniquement après succès avec zéro résultat ;
- ErrorState sur échec ;
- bouton Réessayer ;
- message non technique ;
- log structuré côté serveur sans donnée sensible.

Tester :
- 200 vide ;
- 200 avec données ;
- 401 ;
- 403 ;
- 500 ;
- timeout / réseau indisponible ;
- retry réussi.

5.4 CMD-01 / CMD-02 — CTA SAV et retour POS

Dans le hub /commandes/[id] :
- CTA « Créer une réclamation » vers /reclamations?commande=<id> ;
- lien vers les réclamations filtrées pour cette commande ;
- CTA de reconfiguration POS uniquement si techniquement valide ;
- conserver l’identifiant nécessaire au préremplissage ;
- contrôler les permissions avant affichage ;
- fournir un retour vers la commande depuis la réclamation.

5.5 Deep-links bidirectionnels

Vérifier la navigation :
- Client → POS prérempli ;
- POS → Panier ;
- Panier → Devis ;
- Devis → Commande ;
- Commande → Réclamation ;
- Réclamation → Commande ;
- Commande → Client ;
- Commande → reconfiguration POS si supportée.

Tous les paramètres URL doivent être :
- validés ;
- encodés ;
- ignorés proprement s’ils sont invalides ;
- compatibles avec refresh et ouverture dans un nouvel onglet.

5.6 REC-04 — E2E SAV

Créer un scénario E2E déterministe :
1. authentification avec rôle autorisé ;
2. ouverture d’une commande ;
3. clic Créer une réclamation ;

5. saisie et validation ;
6. création réussie ;
7. affichage dans la liste ;

7. PHASE 5 — PANIER SERVER-FIRST
================================================================================

7.1 PAN-01 — source de vérité

La source de vérité doit être /api/cart :
- le serveur possède articles, variantes, quantités, prix validés et totaux ;
- localStorage devient cache/offline seulement ;
- le client ne décide jamais du prix final ;
- après login, refresh, changement d’onglet ou reconnexion, réconciliation serveur ;
- les erreurs de synchronisation sont visibles et récupérables.

7.2 Migration douce de la clé legacy

Ne pas supprimer la clé immédiatement.
Mettre en place une migration versionnée et idempotente :
1. détecter cache legacy ;
2. parser en sécurité ;
3. envoyer les lignes au serveur pour validation ;
4. recevoir le panier canonique ;
5. marquer la migration réussie ;
6. conserver une compatibilité de lecture limitée si nécessaire ;
7. ne jamais boucler ni dupliquer les lignes.

Ne stocker aucun secret ou champ sensible en localStorage.

7.3 PAN-02 — validateAndMerge obligatoire

Avant checkout et lors de toute réconciliation :
- appeler validateAndMerge côté serveur ;
- recharger prix, disponibilité, variantes et règles courantes ;
- signaler les articles modifiés ou indisponibles ;
- demander confirmation si le total change ;
- bloquer checkout tant que la validation échoue ;
- rendre l’opération idempotente.

7.4 Concurrence et fiabilité

Tester :
- deux onglets ;
- refresh ;
- session expirée ;
- réseau hors ligne puis retour ;
- article supprimé ;
- prix modifié ;
- quantité hors limite ;
- double clic checkout ;
- reprise d’un panier legacy ;
- deux mises à jour concurrentes.

Utiliser version/revision/updatedAt ou mécanisme existant pour prévenir les
écrasements silencieux.

8. PHASE 6 — REFACTORING POS ET MOTEUR DE PRIX
================================================================================

8.1 Principe de refactoring

Le but n’est pas de déplacer 2600 lignes dans un seul autre fichier.
Créer des frontières métier testables, avec API stable.

Avant extraction :
- cartographier états, effets, callbacks et appels réseau ;
- identifier les dépendances circulaires ;
- figer les contrats avec tests ;
- mesurer taille et complexité ;
- ne modifier aucun résultat métier.

8.2 POS-01 — découpage du configurateur

Adapter les noms à l’architecture réelle, mais viser des responsabilités séparées :
- shell/orchestrateur de page ;
- chargement article et permission gates ;
- configuration options/variantes ;
- grand format / dimensions ;
- aperçu et résumé prix ;
- intégration panier ;
- erreurs et états réseau ;
- hooks de calcul/simulation ;
- types et schémas partagés.

Critères :
- aucun module logique cible au-delà d’environ 400 lignes sans justification ;
- le fichier route/page reste un orchestrateur ;
- logique métier hors JSX ;
- effets réseau isolés ;
- pas de prop drilling excessif : préférer composition/context local ciblé ;
- pas de store global pour un état strictement local ;
- composants accessibles et testables ;
- aucune nouvelle dépendance lourde sans justification.

8.3 POS-02 — router calculate.ts par famille

Figer d’abord le contrat public actuel.
Introduire progressivement :
- types d’entrée/sortie canoniques ;
- validation des unités ;
- registre/routeur de famille ;
- stratégie par famille ;
- primitives communes : quantité, surface, minimum, palier, arrondi, remise ;
- erreurs métier typées ;
- fallback explicite seulement pour familles reconnues legacy.

Exemple conceptuel, à adapter sans imposer ces noms :
- pricing/index ou public facade ;
- pricing/router ;
- pricing/common ;
- pricing/families/<family> ;
- pricing/schemas ;
- pricing/errors.

Interdictions :
- switch géant déplacé tel quel ;
- duplication de formules ;
- imports du moteur vers l’UI ;
- accès direct base depuis fonctions pures ;
- prix codés en dur ;
- fallback numérique silencieux ;
- changement d’arrondi implicite.

8.4 Tests de parité prix

Créer une matrice couvrant les familles réelles :
- valeurs normales ;
- quantité minimale ;
- juste avant/après un palier ;
- dimensions décimales ;
- unités différentes ;
- options et finitions ;
- remise autorisée ;
- remise interdite ;
- minimum commercial ;
- arrondi ;
- entrée invalide ;
- famille inconnue ;
- valeurs extrêmes bornées.

Comparer ancien moteur et nouveau moteur pendant la transition.
Toute différence doit être :
- expliquée ;
- validée métier ;
- documentée ;
- testée.
Sinon, c’est une régression à corriger.

8.5 Observabilité

Ajouter sans donnée sensible :
- erreur structurée par code ;
- famille et version de formule ;
- durée de calcul agrégée si infrastructure existante ;
- compteur de fallback legacy ;
- aucun détail de marge dans les logs non autorisés.
