ULTRA-PROMPT CURSOR — REFONTE TOTALE DU BACK-OFFICE ADMINISTRATION
CATALOGUE, MATIÈRES, FORMATS, COÛTS, PRIX & RÈGLES
SYNCHRONISATION UNIQUE AVEC LE POS COMMERCIAL — ANS CRM V3 / ORION

RÔLES À CUMULER

Agis simultanément comme :
- architecte logiciel senior ;
- expert ERP, catalogue, tarification et stock ;
- product designer UX/UI senior ;
- développeur full-stack Next.js / React / TypeScript / Prisma ;
- spécialiste accessibilité WCAG ;
- data analyst chargé de la cohérence des données ;
- ingénieur QA et tests de non-régression ;
- expert sécurité, performance et observabilité.

MISSION

Auditer puis reconstruire réellement le back-office Administration d’ANS CRM V3, avec une priorité absolue sur :
- Catalogue et fiches articles ;
- Matières, formats et coûts ;
- Prix, formules et règles ;
- options et finitions ;
- publication commerciale ;
- synchronisation avec Commercial > POS ;
- cohérence Panier, Devis, Commande, Production et Stock.

Le but n’est pas de produire une simple proposition visuelle ni un rapport théorique. Le but est d’implémenter une refonte utilisable, cohérente, testée, fluide et administrable sans intervention d’un développeur pour les opérations métier courantes.

L’administrateur doit pouvoir, depuis des écrans simples et fiables :
- créer et modifier un produit ;
- organiser les catégories et familles ;
- créer ou corriger une matière et ses déclinaisons ;
- définir formats, grammages, épaisseurs, laizes, couleurs et unités ;
- saisir et maintenir coûts, pertes, charges et prix ;
- associer les matières autorisées à un produit ;
- configurer une formule de calcul sans écrire du code ;
- simuler exactement un prix ;
- vérifier la marge réelle ;
- publier une version tarifaire ;
- contrôler ce qui apparaît dans le POS Commercial ;
- diagnostiquer et corriger les divergences ;
- importer et exporter les données ;
- retrouver l’historique et restaurer une version sûre.

RÉSULTAT FINAL ATTENDU

Le système cible doit appliquer cette chaîne unique :

Administration canonique
→ validation métier
→ version publiée immuable
→ projection commerciale POS
→ configurateur POS
→ pricingResolver serveur
→ panier
→ devis
→ commande figée
→ production
→ réservation et mouvements de stock

Le POS Commercial ne doit pas posséder un catalogue ou un moteur de prix parallèle. Il consomme la projection publiée de l’Administration et appelle le même service de calcul que l’Administration, le panier et les devis.

1. RÈGLES ABSOLUES ET NON NÉGOCIABLES
======================================================================

1. Ne créer aucun prix fictif, aucune donnée mockée et aucun seed destiné à masquer des données absentes.
2. Ne pas remplacer les données réelles par des exemples temporaires.
3. Ne pas casser les formules, règles, identifiants, SKU, historiques, anciennes commandes ou anciens devis.
4. Ne pas modifier silencieusement le résultat d’une formule existante.
5. Toute modification d’une formule publiée crée une nouvelle version.
6. Une commande et un devis validés conservent leur instantané de prix, même si le tarif courant change ensuite.
7. Ne pas supprimer de table, colonne, API ou service avant d’avoir cartographié tous ses consommateurs.
8. Ne supprimer une duplication qu’après migration, compatibilité, validation et test de non-régression.
9. Ne pas mettre de logique tarifaire métier importante uniquement dans React.
10. Tous les calculs officiels doivent être exécutés côté serveur avec des décimales fiables et une politique d’arrondi explicite.
11. Une seule source canonique doit exister pour chaque donnée métier.
12. L’Administration est l’espace d’édition ; le POS Commercial est un consommateur de données publiées.
13. Le POS ne doit pas modifier directement une matière, un coût, une formule ou un prix canonique.
14. Une matière n’est pas automatiquement un article POS.
15. Seules les matières réellement vendues seules peuvent être exposées comme articles de vente directe.
16. Le stock disponible ne doit pas être réécrit directement dans une cellule. Toute correction crée un StockMovement traçable.
17. Ne pas sauvegarder une valeur critique à chaque frappe. Utiliser un mode édition, une validation, un résumé des changements et un enregistrement transactionnel.
18. Aucune publication si une dépendance obligatoire est absente ou invalide.
19. En cas d’échec de publication, conserver la dernière version publiée valide.
20. En cas d’échec de synchronisation, afficher l’erreur et ne jamais prétendre que le POS est synchronisé.
21. Toutes les mutations sensibles créent un audit log : acteur, date, ancienne valeur, nouvelle valeur, motif, objet, version et résultat.
22. Préserver les permissions et appliquer une autorisation par ressource.
23. Ne jamais exposer de secret, fichier .env, token, base réelle ou donnée personnelle dans les journaux ou livrables.
24. Ajouter un test de non-régression pour chaque défaut corrigé.
25. Ne considère pas la mission terminée tant que les validations applicables ne passent pas.

7. MODÈLE FINANCIER ET DÉFINITIONS NON AMBIGUËS
======================================================================

Ne pas utiliser un seul champ « marge » pour plusieurs notions.

Définir et afficher explicitement :

Coût d’achat : montant facturé par le fournisseur dans l’unité d’achat.

Coût matière normalisé : coût ramené à l’unité de consommation après conversions.

Coût de transformation : impression, découpe, pose, façonnage ou autre opération.

Coût complet :
coût matière + transformation + main-d’œuvre + pertes + charges imputées + autres coûts applicables.

Bénéfice réel :
prix de vente HT – coût complet.

Taux de marge sur coût :
bénéfice réel / coût complet × 100.

Taux de marque sur vente :
bénéfice réel / prix de vente HT × 100.

Coefficient multiplicateur :
prix de vente HT / coût complet.

Prix recommandé : prix calculé selon la politique choisie, avant éventuelle validation ou surcharge manuelle.

Prix publié : prix ou règle effectivement utilisée par la version commerciale publiée.

Chaque pourcentage doit préciser sa base :
- sur coût matière ;
- sur coût complet ;
- sur prix de vente ;
- sur sous-total ;
- avant ou après perte ;
- avant ou après remise.

Ne pas appliquer « 30 % + 10 % » sans définir la base et l’ordre. Le détail du calcul doit montrer chaque étape.

Utiliser Decimal ou une solution équivalente pour les montants. Centraliser :
- devise ;
- précision ;
- arrondi par étape ou en fin ;
- arrondi commercial ;
- seuil minimum ;
- règles fiscales si présentes.

5. détecter doublons et conflits ;

11. SYNCHRONISATION ADMINISTRATION ↔ POS COMMERCIAL
======================================================================

La « synchronisation » ne doit pas être une copie fragile entre deux catalogues modifiables.

Architecture cible :
- Administration édite les brouillons canoniques ;
- une publication valide crée une version immuable ;
- une projection commerciale optimisée est générée ;
- le POS lit cette projection ;
- le calcul appelle le pricingResolver avec la version publiée ;
- le POS ne réécrit pas la source Admin.

La projection commerciale contient uniquement ce qui est nécessaire :
- productId ;
- publicationVersionId ;
- nom et contenu commercial ;
- catégorie et ordre ;
- image / maquette ;
- options autorisées ;
- valeurs par défaut ;
- contraintes ;
- matières et formats autorisés ;
- type tarifaire ;
- prix d’appel calculable ou état « sur devis » ;
- disponibilité ;
- hash de cohérence.

Publication atomique :
1. charger le brouillon ;
2. valider les dépendances ;
3. exécuter les scénarios de référence ;
4. générer la version ;
5. générer la projection POS ;
6. calculer le hash ;
7. écrire version et projection dans une transaction ;
8. invalider les caches après commit ;
9. vérifier la lecture ;
10. marquer « Publié et synchronisé » uniquement en cas de succès complet.

Si une étape échoue :
- rollback ;
- conserver la dernière version valide ;
- afficher l’étape fautive ;
- créer une anomalie ;
- permettre de relancer sans duplication.

États de synchronisation :
- Synchronisé ;
- Modifications non publiées ;
- Publication requise ;
- En cours ;
- Erreur ;
- Version POS obsolète ;
- Non applicable.

Ne pas ajouter un gros bouton « Synchroniser POS » partout. L’action principale est « Publier ». La synchronisation technique suit la publication. Un bouton « Relancer » n’apparaît que lors d’un échec explicite.
